# Lab Extension Memo

## 1. What We Extended
*3–5 sentences. Be specific: name the exact node, function, parameter, dataset, and/or architecture changes you made/would make relative to the baseline lab — not "we improved it." Think about efficiencies and effectiveness of the solution not the value of the lab experience.*

The baseline stored artist, album, year, genre, and score on every Chroma chunk, but `ConversationalRetrievalChain` passed only the review text to the model. This left most excerpts anonymous: among the first 300 reviews, only 21.6% of chunks named their artist and 17.0% named their album. We added `format_context()` to label every excerpt and added `parse_filters()` and `build_where()` to translate requests such as “rock albums from the 1990s” into Chroma metadata filters, including compound genres such as “Electronic / Rock.” For the Gradio app, we added MMR retrieval (`k=4`, `fetch_k=20`, `lambda_mult=0.5`), a confidence gate before `phi3`, `[Source N]` citations, and a `source_id` for each review. Finally, we moved the shared logic into `musicRagCore.py`, fixed Gradio’s missing embedding function, and added `condense_question()` so follow-up questions keep earlier constraints.

## 2. Why We Made This Choice
*What alternative(s) did you consider and reject? Why this one instead of those?*

**Regex-only filter parsing** — what we did in Lab 1, and reliable for a bare "2019", but every phrasing needs its own rule ("the 90s", "after 2015", "hip hop", "top rated"); the model handles those translations for free, so we kept a keyword check (`GENRE_WORDS`, `SCORE_WORDS`) only as a *guard* on the model's output rather than as the parser.
**Instructing the model not to invent filters** — tried first and it failed: "Tell me about Kid A" still became Rock + 2000, which hides the reissue review, and it broke "perfect 10" by returning 9.0, so the prompt rule became a code guard.
**LangChain's `SelfQueryRetriever`** — the same idea packaged, but it needs `lark`, and its generic query grammar is harder for a small local model to emit reliably than our four-key JSON.
**Re-embedding year and genre into the chunk text** — would help the search *notice* a year but still can't guarantee a match, and costs a 21-minute rebuild; a `where` clause guarantees it with no rebuild at all.
**Simply raising `k`** instead of MMR — more chunks make the prompt noisier rather than more varied, and `phi3`'s context fills fast.
**Skipping the confidence gate whenever a filter matched** — tempting, since a matched filter guarantees on-topic chunks, but it would wave through "What is the capital of France?" any time the parser happened to extract something; we re-tuned the threshold instead.
**Copying the filter functions into the Gradio app** — the two `qa_prompt`s had already drifted apart once, which is exactly the evidence that a second copy drifts again, so both chatbots import one definition instead.

## 3. Benefits
*What does this improve, and how would you show it — a number, a case that now passes, a before/after comparison?*

Across 15 questions that name a year, genre and/or score, the share of the top 10 retrieved chunks whose metadata actually satisfies the request went from 16/150 (11%) to 140/150 (93%) on the terminal chatbot, and from 5/60 (8%) to 56/60 (93%) on the Gradio app at `k=4`; `parse_filters()` extracted exactly the filters a careful reader would on 15/15 of them, and left all five no-filter questions untouched at 10/10 identical results. The instructor's own demo question, "What are some critically acclaimed albums from 2023?", went from 0/10 matching chunks to 10/10, and the Gradio app went from answering *nothing at all* — every question raised the MMR `ValueError` — to answering normally. Re-measuring the confidence gate over 20 answerable and 10 unanswerable questions moved it from the eyeballed 0.5 to 0.35, cutting wrongly refused filter questions from 6/15 to 0/15 while raising overall accept/refuse accuracy from 80% to 90%. The follow-up fix shows best as a case: "Recommend some jazz albums" followed by "Which of those is the highest rated?" used to search on `{'min_score': 9.0}` with the Jazz constraint lost, returning Viktor Vaughn, Faust, Mastodon and Peter Gabriel while the answer named a Coltrane record lifted from the previous turn's text, and now searches `{'genre': 'Jazz', 'min_score': 9.0}` and returns four jazz reviews in which *A Love Supreme* is genuinely Source 1.

## 4. Drawbacks & Tradeoffs
*What does this cost or risk — complexity, latency, $, a new failure mode, less generalizable?*

Every question now pays a second LLM call before the search, averaging about 5 seconds for filter extraction, and a follow-up pays a third for the rewrite — which is itself a new failure mode, since a bad rewrite corrupts the filters and the query together where before only the follow-up was weak. The confidence threshold is a compromise rather than a fix: the answerable and unanswerable score distributions overlap (lowest real question 0.383, highest nonsense question 0.417), so 3 of 10 off-topic questions still get through at 0.35, and that value was swept on the Gradio configuration (MMR, `k=4`) while the terminal chatbot now applies the same gate to plain search at `k=10` without a re-sweep. Two things in the repo are out of step with the measurements: the `source_id` traceability is inert until someone rebuilds, because the collection on disk predates it and reports `None` on every chunk, and `embedMusicChunks.py` now prefers `pitchfork_reviews_v2.xlsx` (25,107 reviews, scores 0.0–10.0) over the `v3` workbook every number here was measured on (1,854 reviews, scores 8.5–10.0), so a rebuild would silently change the corpus underneath the whole memo. Two dataset problems we did not solve at all are worth naming: because v3 contains only reviews scoring 8.5 and above, "is this album any good?" has exactly one possible answer, and the `year` column means the review year for 76.5% of rows but the release year for reissues, so a year filter is quietly answering a different question than the user asked.
