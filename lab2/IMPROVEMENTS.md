## Improvement 1: Metadata Headers on Retrieved Chunks

1. What we extended (specifically):
We added a `document_prompt` PromptTemplate to the `combine_docs_chain_kwargs` argument of `ConversationalRetrievalChain.from_llm()` in `musicChatbot.py`. This parameter controls how each retrieved document is formatted before being concatenated into the `{context}` block of the main prompt. The new format prepends a structured header — `[Artist - Album | Score: X | Genre: Y | Year: Z]` — to every chunk. We also added a `MetadataNormalizingRetriever` wrapper class around the base ChromaDB retriever to replace any `None` metadata values with `"Unknown"` before the document prompt attempts to format them.

2. Why we made this choice (and not something else):
The alternative was to embed the metadata directly into each chunk's text at indexing time (in `embedMusicChunks.py`) so it would be stored alongside the review prose. We rejected that because it would require rebuilding the entire ChromaDB from scratch and would permanently inflate every chunk's token count, consuming context window on every query regardless of need. The `document_prompt` approach applies headers at query time with zero re-embedding cost. We also considered adding the metadata only to the system prompt as a lookup table, but that would not scale — the table would grow with every retrieved album and hit token limits quickly.

3. Benefits (compare improvements before/after):
Grounding score (how well answers are anchored in retrieved sources rather than hallucinated) improved from 2/6 to 5/6 across three eval queries. The most concrete gain was on the Radiohead query: before the change, the model said the Pitchfork rating was "not explicitly stated in the context" even though a chunk with score 10.0 was present in the sources. After the change, the model correctly cited three Radiohead albums with accurate scores (In Rainbows 9.3, OK Computer OKNOTOK 10.0, A Moon Shaped Pool 9.1), all drawn from the headers. On the jazz query, every recommendation mapped to an actual source — the baseline had hallucinated Monk and Mingus albums not present in the retrieved chunks.

4. Drawbacks and Tradeoffs (cost or risk):
Each header adds roughly 15–20 tokens per chunk. At k=10 chunks, that is 150–200 extra tokens per query injected into the context window. For a local model like Mistral 7B with a limited context window, this is a non-trivial cost that compounds with conversation history. Relevance score did not improve (3/6 → 2/6) because the headers help the model use what it retrieves but do nothing about *what* gets retrieved — off-topic chunks like Ragga Twins still appear in a jazz query. The rainy day query also showed the model can still hallucinate reasoning around a correct source (it claimed "In Rainbows" is rainy-day music based on the word "Rain" in the title, which is a stretch). Headers anchor attribution but do not prevent interpretive hallucination.


## Improvement 2: MMR (Maximum Marginal Relevance) Retrieval

1. What we extended (specifically):
We changed the `search_type` parameter on `vectorstore.as_retriever()` in `musicChatbot.py` from the default cosine similarity to `"mmr"`, and added `fetch_k=30` to the `search_kwargs` dict. MMR requires the embedding function at query time for re-ranking, so we also added a `LocalEmbeddings` class — a thin wrapper around `sentence-transformers` implementing LangChain's `Embeddings` interface — and passed it to the `Chroma` constructor via `embedding_function=embeddings`. The `LocalEmbeddings` class uses the same `all-mpnet-base-v2` model used during indexing in `embedMusicChunks.py` to keep query vectors comparable to stored document vectors.

2. Why we made this choice (and not something else):
The baseline and post-Improvement-1 results showed repeated albums filling multiple context slots: in the jazz query, Ornette Coleman and Matthew Shipp each appeared twice out of 10 chunks, wasting context on redundant text. The alternative was to post-filter duplicate albums after retrieval — check the metadata and drop any chunk whose album already appeared. We rejected that because it reduces effective k unpredictably (a query could end up with only 4 usable chunks if 6 are from the same album) without giving the model better replacements. MMR replaces the duplicates with the next-best diverse candidates from a larger fetch pool, keeping k stable at 10.

3. Benefits (compare improvements before/after):
On the jazz query, MMR eliminated all duplicate album retrievals and introduced Keith Jarrett as a new diverse recommendation not present before. Total grounding held at 2/2 and relevance at 1/2 for that query — flat but with higher quality diversity in the jazz results. Overall scores: grounding 2/6, relevance 1/6 after MMR vs. 5/6 and 2/6 after Improvement 1. The Radiohead and rainy day queries both regressed significantly (see drawbacks).

4. Drawbacks and Tradeoffs (cost or risk):
MMR is the wrong tool for specific-artist queries. When a user asks about Radiohead, multiple chunks about Radiohead are inherently similar — they're all from the same band's reviews. MMR's diversity algorithm treats that similarity as redundancy and removes those chunks in favor of unrelated albums. After MMR, the Radiohead query retrieved zero actual Radiohead chunks (vs. three in Improvement 1), and the model correctly reported finding no review, then hallucinated album names from training data. Grounding on that query dropped from 2/2 to 0/2. The rainy day query similarly lost its grounding anchors and returned to full hallucination. MMR improves broad genre queries at the direct expense of specific artist or album lookup queries. A production system would need query-intent detection to apply MMR selectively — only for broad queries, not for named-entity lookups. We also tuned `fetch_k=30` by eye with no systematic sweep; a larger pool might partially mitigate the regression on specific queries but would increase retrieval latency.


## Improvement 3: Genre-Aware Metadata Filtering

1. What we extended (specifically):
We extended `MetadataNormalizingRetriever._get_relevant_documents()` in `musicChatbot.py` to perform genre-aware retrieval. We added a `GENRE_KEYWORDS` dict mapping plain-English query words (e.g. "jazz", "rock", "hip hop") to genre substrings stored in the ChromaDB metadata field. A new helper function `_detect_genre_keyword()` scans the lowercased query for any match. When a genre is detected, the retriever fetches `k*4 = 40` candidates by semantic similarity, then post-filters in Python using a case-insensitive substring check (`genre_keyword.lower() in doc.metadata["genre"].lower()`), keeping the top k genre-matching results. If fewer than k genre matches are found, it falls back to the unfiltered top-k. Queries with no genre keyword (e.g. artist lookups, mood queries) follow the original unfiltered similarity search path unchanged. Note: we initially attempted to use ChromaDB's `{"genre": {"$contains": "Jazz"}}` where-clause, but discovered that `$contains` is a document-content operator in ChromaDB's API and does not apply to metadata fields, returning zero results silently. The Python post-filter approach was adopted as a reliable alternative.

2. Why we made this choice (and not something else):
The alternative was to use ChromaDB's native metadata `$in` operator with a pre-defined list of all jazz genre values (e.g. `{"genre": {"$in": ["Jazz", "Experimental / Jazz", "Jazz / Experimental", "Electronic / Jazz"]}}`). We rejected this because it requires enumerating all genre variants in the database ahead of time, is brittle when new compound genres appear, and requires a separate database inspection step. The Python post-filter approach is more robust: it uses simple string containment which naturally handles all compound genre values and requires no knowledge of the full genre taxonomy. The cost is fetching a larger initial candidate pool (40 instead of 10), but ChromaDB's similarity search is fast enough that this is negligible at this dataset size.

3. Benefits (compare improvements before/after):
Relevance score improved from 2/6 to 3/6 overall. The jazz query showed the most concrete gain: before this improvement, 4 of 10 retrieved sources were off-genre (Tropicália, Ragga Twins, Peanut Butter Wolf, Destroyer). After, all 10 retrieved sources were tagged as Jazz or Experimental/Jazz in the metadata, and every album the model recommended mapped directly to a source. Relevance for that query went from 1/2 to 2/2. Grounding held at 5/6. The Radiohead and rainy-day queries were unaffected since neither contains a genre keyword — they follow the same retrieval path as Improvement 1.

4. Drawbacks and Tradeoffs (cost or risk):
The genre keyword list in `GENRE_KEYWORDS` was defined by hand and covers only the genres we anticipated. A query like "I want some bebop" or "recommend some bossa nova" would not trigger the jazz filter and would fall back to unfiltered search. The list also has ambiguous mappings: "pop" maps to "Pop/R&B," which could incorrectly filter out rock albums that are commercially popular. Ornette Coleman still appeared three times in the jazz query results and Matthew Shipp twice — the filter fixes off-genre noise but does not address within-genre redundancy, which would require combining this with MMR on the filtered pool. The rainy-day query showed continued chat-history bleed: because the previous query was about Radiohead, the chain's question reformulation pulled Radiohead chunks into the rainy-day results, producing a response that recommended In Rainbows based on the word "rain" in the album title rather than actual mood-matching content.


## Improvement 4: Hybrid BM25 + Dense Retrieval

1. What we extended (specifically):
We extended `MetadataNormalizingRetriever._get_relevant_documents()` in `musicChatbot.py` to run a hybrid retrieval path for non-genre queries. At startup, the full ChromaDB corpus is loaded via paginated `collection.get()` calls (batches of 5,000 to avoid SQLite's variable-count limit) and indexed with `BM25Okapi` from the `rank_bm25` library. In the retriever, non-genre queries now run two searches in parallel: the existing dense similarity search (`k*2 = 20` candidates) and a BM25 keyword search (`k*2 = 20` candidates). Results are merged using a `_reciprocal_rank_fusion()` helper: each document's final score is the sum of `1 / (rank + 60)` across both ranked lists, and the top `k = 10` documents by RRF score are returned. Genre queries (e.g. jazz) bypass BM25 entirely and continue using the Python-filtered dense path from Improvement 3.

2. Why we made this choice (and not something else):
The gap this targets is exact artist-name lookup: dense embeddings capture semantic meaning but can miss exact proper nouns like "Radiohead" if the query embedding lands closer to general rock-music vectors than to Radiohead-specific review vectors. BM25 solves this by counting exact term occurrences, so a query containing "Radiohead" directly boosts every chunk that contains that word. The alternative was LangChain's `EnsembleRetriever` with `BM25Retriever` from `langchain_community` — we rejected that because it requires an additional package not already installed, and `langchain_community` has a large dependency footprint relative to the benefit. Building BM25 directly from `rank_bm25` let us control the merge logic and keep the genre-filter fast path intact. Reciprocal Rank Fusion (RRF) was chosen over weighted score averaging because the two retrievers produce incommensurable scores (cosine similarity vs. BM25 relevance scores), whereas RRF operates only on rank positions.

3. Benefits (compare improvements before/after):
Overall: Grounding 4/6, Relevance 4/6, compared to Grounding 5/6, Relevance 3/6 after Improvement 3 — net roughly flat (relevance +1, grounding −1). Jazz query held at 2/2 grounding and 2/2 relevance, confirming the genre filter path was unaffected. Radiohead relevance improved: 3/10 retrieved sources were actual Radiohead reviews, up from 0/10 in the MMR run and providing enough anchors for the model to name specific albums. The model correctly cited OK Computer and Hail to the Thief with accurate scores drawn from sources.

4. Drawbacks and Tradeoffs (cost or risk):
BM25 adds a 5–10 second startup cost to build the index over the full corpus. More importantly, the Radiohead grounding score dropped from an estimated 2/2 (after Improvement 1) to 1/2: the model listed In Rainbows, Kid A, and Amnesiac with specific Pitchfork scores (8.7, 9.3, 9.1) that are correct from its training data but were not present in the retrieved sources — this is training-data leakage invited by the broader question phrasing ("What did Pitchfork say about Radiohead?" vs. "What are some good Radiohead albums?"). The rainy-day query still suffers from conversation-history bleed: `ConversationalRetrievalChain` reformulates queries using prior chat turns, and the Radiohead context from Q2 bled into Q3, producing a Radiohead-heavy source list for a mood query. BM25 also has no impact on this problem since the chain's question reformulation happens before the retriever is called, potentially diluting or removing the exact keyword BM25 relies on.


## Improvement 5: HyDE (Hypothetical Document Embeddings)

1. What we extended (specifically):
We added a `HYDE_PROMPT` PromptTemplate and a `_generate_hypothetical_document(query)` helper function in `musicChatbot.py`. In `MetadataNormalizingRetriever._get_relevant_documents()`, the non-genre path now calls `_generate_hypothetical_document(query)` before the dense similarity search, using the returned hypothetical as the search string instead of the raw query. The function asks Mistral 7B to write a 2–3 sentence Pitchfork-style review excerpt that would answer the given request, then passes that generated text to `vectorstore.similarity_search()`. The BM25 leg is unchanged — it still tokenizes and scores the original query. Genre queries bypass HyDE entirely via the existing genre-filter path. A try/except in the helper falls back to the original query if the LLM call fails.

2. Why we made this choice (and not something else):
The persistent problems after Improvements 1–4 were (a) conversation-history bleed on the rainy-day query (Radiohead vocabulary from Q2 contaminating Q3 retrieval) and (b) grounding failures where the model cited albums not present in retrieved sources. Both trace to the same root: the raw query embedding sits far from the actual review text in vector space. User phrases like "something for a rainy day" share almost no vocabulary with Pitchfork review prose, so the dense search retrieves high-scoring popular chunks rather than mood-matched ones. HyDE bridges that gap by generating text in the same vocabulary as the corpus before embedding. The alternative was query expansion — generating several synonym/paraphrase variants and merging their results. We rejected that because it requires multiple retrieval calls (one per expansion), multiplying latency, while HyDE produces a single search string at the cost of one LLM call. Cross-encoder reranking was the other candidate, but rerankers fix ordering after retrieval — they cannot introduce albums absent from the initial candidate pool, which is the actual failure mode here.

3. Benefits (compare improvements before/after):
Grounding improved from 4/6 to 6/6 (perfect) and relevance from 4/6 to 5/6 — the largest gain of any single improvement. The rainy-day query was the clearest win: history bleed was fully eliminated because the hypothetical review never mentioned Radiohead, breaking the embedding's contextual dependency on the prior query. The sources for that query changed from a Radiohead-dominated list to a genre-diverse set of mood-appropriate albums (Built to Spill "downtempo ballads", Wilderness "rainswept instrumentation", Angel Olsen, Milton Nascimento, Bruce Springsteen Nebraska). The model recommended five albums all traceable to retrieved sources with no hallucination. The Radiohead query also improved on grounding: the model limited its answer strictly to the two Radiohead reviews actually retrieved (Hail to the Thief, A Moon Shaped Pool), citing accurate scores, with no invented albums — a direct improvement over the three hallucinated albums (In Rainbows, Kid A, Amnesiac with specific scores) that appeared in Improvement 4's run.

4. Drawbacks and Tradeoffs (cost or risk):
HyDE adds one full LLM call per non-genre query before retrieval even begins, roughly doubling per-query latency on CPU (from ~15–30 seconds to ~30–60 seconds on Mistral 7B). For a production deployment this would be the dominant cost concern. HyDE also hurt Radiohead relevance: only 2/10 retrieved sources were actual Radiohead reviews (down from 3/10 after Improvement 4). The hypothetical review described Radiohead's electronic-experimental sound, which semantically matched other experimental rock albums like Bon Iver's *22, A Million* and Keith Fullerton Whitman more than Radiohead-specific chunks — because those non-Radiohead albums shared the generated vocabulary. This is HyDE's fundamental tension with named-entity queries: the hypothetical smooths over the exact name and emphasizes sound description instead, weakening the one signal BM25 would have caught cleanly if the dense leg hadn't diluted the RRF pool. The quality of the hypothetical is also entirely dependent on the LLM's knowledge of the topic — if Mistral generates a poorly matched or factually incorrect hypothetical, retrieval degrades silently with no error signal.
